# `:hover`는 왜 한 번도 매칭된 적이 없는가

계획서 **Phase 2-3** — "`set_focus` / `set_hover`를 프로덕션 경로에 연결" — 중 hover 쪽.

## 요약

`DomRenderer::set_hover()`는 구현돼 있었지만 **호출하는 프로덕션 코드가 없었다.** 호출부는
전부 `dom/renderer/tests.rs`, `dom/query.rs`, doc 예제, 그리고 Phase 0에서 추가한
`PipelineHarness::hover()`뿐이다. 즉 실행 중인 앱에서 `NodeState.hovered`는 항상 `false`였고,
`Button:hover { ... }`는 **문서에는 있지만 화면에는 없는 기능**이었다.

연결하려면 세 가지가 필요했고, 그 과정에서 두 개의 기존 버그가 드러났다.

| | | 상태 |
|---|---|---|
| **H-1** | 좌표 → 노드를 답할 수단이 없다 | ✅ 페인트 기록 |
| **H-2** | `Event::Mouse`를 아무도 처리하지 않는다 | ✅ 배선 |
| **H-3** | hover가 떠난 노드에 스타일이 눌어붙는다 | ✅ 고침 |
| **H-4** | `:hover`가 조상에 전파되지 않는다 | ✅ 고침 |

## H-1 — 히트 테스트는 무엇을 근거로 답하는가

두 가지 후보가 있었다.

**(A) 레이아웃 엔진의 rect.** `L-1`을 고친 뒤로 엔진은 실제로 트리 전체를 계산한다. 하지만
그 결과는 화면과 다르다 — 컨테이너가 자기 배치를 직접 계산하고, 위젯의 배치 의도가 DOM
스타일에 실리지 않기 때문이다(`findings-layout.md`의 `L-2`, `L-3`). 엔진에 물어보면 사용자가
클릭한 곳과 다른 답이 나온다.

**(B) 페인트 패스가 기록한 area.** 페인트 패스는 노드의 정체성과 그 노드가 실제로 받은
area를 **동시에** 아는 유일한 지점이다. 사용자가 클릭하는 것은 그려진 것이므로, 그려진 것을
기록한다.

**(B)를 택했다.** `DomRenderer::hit_map: Vec<(DomId, Rect)>`에 페인트 순서대로 쌓는다.

- 전위 순회이므로 부모가 자식보다, 앞 형제가 뒤 형제보다 먼저 들어간다. **역방향으로
  스캔**하면 가장 나중에 그려진 = 위에 있는 노드가 먼저 나온다.
- `overflow: hidden` 클립과 교집합을 취한다. 클립 밖으로 완전히 밀려난 노드는 화면에 없으므로
  기록하지 않는다.
- `css_layout`의 박스 조정이 끝난 **뒤의** area를 기록한다. 마진으로 밀린 위젯은 밀린 자리에서
  잡힌다.
- 매 프레임 `clear()`만 하고 용량은 재사용한다.

`dom_from_render`가 꺼져 있으면 루트 말고는 노드와 area가 연결되는 지점이 없다. 그래서
히트 테스트는 그 플래그를 필요로 하고, 없으면 `None`을 답한다 — 어차피 그 경로에서는
`:hover`가 매칭될 노드도 없었다.

**한계:** 오버레이(드롭다운, 툴팁, 토스트)는 메인 패스 뒤에 버퍼로 직접 그려지므로 기록되지
않는다. 오버레이 위의 점은 그 아래 것으로 해석된다.

## H-2 — `Event::Mouse`가 아무 데도 가지 않았다

`App::handle_event`는 `Key`, `Resize`, `Tick`만 처리했다. `Mouse`는 사용자 핸들러에 전달된 뒤
버려졌다. 이제 좌표로 히트 테스트를 돌려 hover를 옮기고, **옮겨졌을 때만** 다시 그린다.

한 위젯 안에서 포인터가 움직이는 것은 프레임 비용이 되지 않는다.

## H-3 — hover가 눌어붙었다 (기존 버그)

`set_hover`는 들어오는 노드의 캐시된 스타일만 지웠다.

```rust
if let Some(id) = new_hover_id {
    self.styles.remove(&id);   // 나가는 노드는?
}
```

떠나는 노드는 `dirty = true`만 찍혔는데, `style_for_with_inheritance`는 **dirty 플래그를 보기
전에 캐시에서 먼저 답한다.** 그래서 포인터가 떠나도 hover 스타일이 그대로 남았다.

또 자기 자신만 지우는 것으로는 부족하다. `compute_subtree_styles`는 깨끗하고 캐시된 노드에서
하강을 멈추므로, `#outer:hover #inner` 같은 후손 규칙과 상속되는 속성이 옛 값에 얼어붙는다.
그래서 **서브트리 전체**를 무효화한다.

형제 결합자(`.a:hover + .b`)는 이 범위 밖이고 여전히 낡은 값을 쓴다.

## H-4 — `:hover`는 조상에도 붙는다 (기존 버그)

`DomTree::set_hovered`는 정확히 한 노드만 표시했다. CSS에서 `:hover`는 포인터 아래 요소와
**그것을 포함하는 모든 요소**에 매칭된다. 버튼의 라벨 위에 포인터가 있으면 버튼도 hover다.

한 노드만 표시하면 `.button:hover`처럼 컨테이너에 붙은 규칙이 전부 죽는다 — 히트 테스트는
언제나 가장 깊은 노드를 답하기 때문이다. 조상 체인 전체를 표시하도록 고쳤다.

`:focus`는 그렇지 않다. 포커스는 정확히 하나이고, 조상 형태는 `:focus-within`이라는 별도
셀렉터다. `set_focused`는 그대로 둔다.

**무효화 범위:** hover가 옮겨지면 상태가 실제로 바뀐 노드는 두 조상 체인의 **대칭차**뿐이다.
분기점 위쪽은 전에도 hover였고 지금도 hover다. 그 부분까지 다시 계산하면 한 컨테이너 안에서
포인터를 움직이는 것만으로 매 프레임 캐스케이드 전체가 돌아간다.

## 비용

노드마다 `Vec` push가 하나 늘고, 마우스가 움직일 때마다 히트 맵을 역방향으로 스캔한다.
`cargo bench --bench frame`, `main` 대비 (`--save-baseline` / `--baseline`, 같은 기계, 다른
작업 없이):

| | 10 | 50 | 200 |
|---|---:|---:|---:|
| `changed` | +1.3% | +0.7% | +0.5% |
| `dom_from_render` | −0.8% | +0.6% | −0.4% |
| `css_layout` | −0.4% | −1.2% | −2.5% |
| `unchanged` | −2.4% | +1.6% | +0.8% |

**전부 잡음이다.** 유의하다고 나온 세 칸 중 둘은 *빨라졌다*고 나오는데, 이 변경으로 빨라질
길은 없다. 히트 맵을 채우는 비용은 이 해상도에서 측정되지 않는다.

기록은 `dom_from_render` 경로에만 존재한다. 기본 경로는 `hit_map.clear()` 한 줄만 만난다.

## 키보드 우선이라는 것

`REV-EVENT-007` / `REV-UX-007`이 지적하듯 TUI의 기본 modality는 키보드다. 이 작업은
`:hover`를 **동작하게** 만들 뿐, 권장 상호작용으로 승격시키지 않는다. hover 전용 정보를
두지 말고, 마우스를 움직이지 않으면 hover가 남는다는 점을 감안해 설계할 것.

## 남은 것

| | |
|---|---|
| **focus 배선** | `set_focus`는 여전히 프로덕션 호출부가 없다. hover와 달리 "포인터 아래"라는 자명한 소스가 없고, 포커스 순서·트랩·복원이 필요하다 — `FocusManager`가 이미 있지만 `App`이 모른다 |
| **클릭 라우팅** | `node_at`은 클릭에도 그대로 쓸 수 있다. 이벤트 라우팅은 계획서상 3.x |
| **오버레이 히트 테스트** | 오버레이가 자기 area를 기록하지 않는다 |
| **형제 결합자 무효화** | `.a:hover + .b`가 낡는다 |

`tests/hit_test.rs`가 위 전부를 고정한다.
